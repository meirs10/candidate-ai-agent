CANDIDATE AI AGENT — COMPLETE PROJECT OVERVIEW

This document is the knowledge base for questions about the software project /
system itself: what it is, how it is built, every major flow, and the
engineering decisions behind it. It also describes how this AI agent itself
works, so that when a recruiter asks the agent second-person questions ("how do
you work?", "what reranker do you use?", "how were you built?", "what model are
you?"), the agent can answer about its own architecture from this document. It
contains no private candidate data, no personal information, and no API keys or
secrets.

A note on "you" and "I": throughout this document, when the agent speaks about
how "I" work or what "I" use, it is describing this very system. Questions about
how the agent/assistant operates, is built, retrieves information, scores
skills, was evaluated, or is deployed are all answered from this document. (In
contrast, "your name", "your skills", "your experience" refer to the candidate's
professional profile, which lives in the candidate's own documents and
structured store, not here.)


WHAT THE PROJECT IS

The Candidate AI Agent is an AI-powered digital representative for a single job
candidate. A recruiter opens a secured, always-available chat link and asks
natural-language questions about the candidate; the agent answers accurately and
professionally, grounded strictly in the candidate's own documents and a trained
machine-learning scoring model. It is deliberately more than a standard "chat
with your PDF" demo: it combines probabilistic multi-tool routing, an advanced
multi-stage Retrieval-Augmented Generation (RAG) pipeline, and a purpose-built,
fine-tuned NLP model for skill-proficiency scoring, all wrapped in a rigorous
multi-dimensional evaluation suite and instrumented with per-turn cost and
latency telemetry.

The problem it solves: recruiters reading a CV cannot tell verified fact from
self-promotion, cannot quickly gauge how strong a candidate actually is in a
given skill, and cannot interrogate a static document. This system turns a pile
of documents into an interactive, grounded, honest representative that cites
real evidence, refuses to answer what it does not know, and quantifies skill
levels with a trained model instead of keyword guessing.

The whole system can run on either a 100% local open-source stack or an all-API
cloud stack, selected purely through configuration with no code changes. The
cloud configuration is what makes it deployable as an always-on, secured,
low-cost service; the local configuration is what made it possible to build,
train, and evaluate everything for free on the developer's own hardware.


THE CORE DESIGN DECISION: BUILD VS SERVE

The single most important architectural decision is the split between a build
phase and a serve phase.

The build phase runs locally and only occasionally. The candidate uploads
documents; the system parses them, performs section-aware chunking, embeds the
chunks into a vector store, generates per-document summaries, and runs the
trained scoring model to score each listed skill. This produces two persistent
artifacts: a ChromaDB vector index (the unstructured knowledge) and a small JSON
structured store of verified facts plus, for each listed skill, the supporting
evidence found in the documents. The model's 1-to-5 score itself is shown to the
candidate as private setup feedback and is deliberately not persisted (see the
skill-proficiency section). All heavyweight machine learning — document parsing, OCR, the
DeBERTa skill scorer, and optionally a local embedder and reranker — only ever
runs in this phase, on the candidate's own machine.

The serve phase is the hosted, always-on recruiter chat. It only reads the
prebuilt artifacts and performs retrieval plus LLM calls. It deliberately
contains no heavy local model, so the serve image is small (no PyTorch, no
transformers, no Unstructured) and fits free or near-free hosting tiers. This
separation is what makes the project simultaneously sophisticated to build and
cheap and simple to host. The lean serve dependencies are listed in
requirements.txt; the full build/eval/training stack is in requirements-dev.txt.


THE USER FLOWS AND PAGES

The application is a multi-page Streamlit app with three pages, two of which a
recruiter can never see.

The Candidate Setup page is for the candidate only. Here the candidate uploads
supporting documents (CV, transcripts, certificates, recommendation letters) in
PDF, DOCX, TXT, MD, PNG, or JPG form; fills in structured profile fields
(contact details, education, experience, job preferences); lists the skills they
want assessed; and triggers skill-proficiency estimation and ingestion. Uploads
are staged rather than ingested on sight: the candidate sets the document type
for each file individually, with a default guessed from the filename, and then
presses a single button to ingest them all. The type matters because it selects
the summary rubric, and staging matters because ingestion costs embedding and
LLM calls — a wrong guess should be corrected before it is paid for, not after.
Files are de-duplicated by a hash of their contents, because Streamlit re-runs
the whole script on every widget interaction and the uploader hands back its
files each time; without the hash, typing in a text field re-ingested everything
already uploaded. This page can edit the profile and run the heavy pipeline, so
in production it is not registered at all — a recruiter can never reach it, edit
the profile, or trigger ingestion.

The Usage and Conversations page is a private dashboard over the telemetry log:
total spend, cost and latency per turn, which tools the router chose, and the
full text of every recruiter conversation. It is registered only for a session
that arrived with the correct admin password, compared with a constant-time
comparison, and it is never part of the normal navigation.

The Recruiter Chat page is the always-on public surface. It is a clean
conversational interface: the recruiter types a question; the agent reasons
about it, decides which tools to call, gathers grounded evidence, and returns a
concise, professional answer in the same language the recruiter used. The chat
maintains conversation history across turns so follow-up questions work
naturally.

Which pages are exposed is controlled by configuration. In production mode only
the recruiter chat is registered with the Streamlit navigation; in setup mode
the setup page is available too, for local profile updates.

The page files live in a directory called app_pages, and the name is a security
control rather than a style choice. Streamlit auto-discovers any directory named
"pages" and publishes every file inside it as its own route, bypassing the main
entry point entirely — which meant the setup page, holding a phone number and a
salary expectation, was reachable on a hosted deployment without ever passing
the access gate. Renaming the directory removes the auto-discovery, and each
page additionally checks authentication itself, so the guarantee does not rest
on a directory name alone.


AGENTIC TOOL CALLING — PROBABILISTIC MULTI-TOOL ROUTING

The system does not blindly query a vector database for every question, and it
does not use a conventional ReAct loop either. It uses probabilistic multi-tool
routing: one scoring call rates every tool independently, and every tool that
clears a threshold runs at once.

A turn works in one pass, with no re-querying loop. First, a single routing call
scores all four tools from 0.0 to 1.0 — an independent probability per tool that
it is needed for this question — and supplies the argument to call each one
with. The scores deliberately do not sum to 1: several tools can be high when a
question genuinely needs several, and all four can be low for an out-of-scope
question. Second, every tool scoring at or above the selection threshold (0.30
by default) is selected, so a close call fires more than one tool rather than
forcing a winner. Third, the selected tools execute concurrently in a thread
pool and their outputs are gathered as context. Fourth, one synthesis call
answers the question from all of that context at once. When no tool clears the
threshold, the agent answers with no context at all, which is what produces a
clean refusal for an out-of-scope question.

The design reason for scoring over choosing: a recruiter question frequently
spans sources — "what's their Python experience and are they available?" needs
the skill evidence and a structured field — and a single-choice router has to
either pick one and be wrong, or take another round trip to add the second. The
router is told explicitly to prefer a small score like 0.3 over a hard 0.0 when
unsure, because missing the right tool costs far more than running a borderline
one.

Result-based escalation is the safety net. If tools were selected but every one
of them came back empty, the router probably missed, so the remaining tools run
and their context is added before synthesis. Emptiness is defined per tool
rather than by a bare string check: a structured field that resolved to "Not
provided", a skill that was not among the assessed ones, or a search that
returned no relevant information. This is a pay-per-need fallback — the common
case still runs only the tools that scored — and in a full 490-question
evaluation run it triggered on a small handful of questions.

Only the final assistant text is persisted into the conversation history, which
keeps the stored history simple and serializable for Streamlit session state.
Each turn also records the per-tool probabilities, which tools ran, their
arguments, and a preview of each result. That trajectory is exactly what the
evaluation suite inspects to judge tool selection, and the same record feeds the
telemetry log described later.


THE FOUR TOOLS

get_structured_data returns fixed, guaranteed-accurate facts from the structured
JSON store: full name, email, country code, phone, LinkedIn, GitHub, education
(degrees, fields, institutions, GPAs), years of experience, current role,
desired job title, job description, monthly salary expectation, preferred
location, availability, work type, and openness to relocation. These are exact
fields, never retrieved or paraphrased.

get_skill_proficiency returns the supporting evidence found in the candidate's
documents for a named skill — the exact passages a retrieval model surfaced for
it at setup time. With no skill named it lists every assessed skill. This is the
tool for any "how good / how strong / how proficient / how skilled / how
experienced" question, or to characterize skills. It intentionally does NOT
return a numeric rating: the trained model's 1-to-5 score is candidate-private
(see below), so the agent describes the evidence qualitatively rather than
quoting a level. If a requested skill was not assessed, the tool says so and the
agent falls back to document search.

search_documents runs the full RAG pipeline over the candidate's unstructured
documents for anything not covered by the other two tools: projects, detailed
experience, what they did with a technology, achievements, certifications, and
richer context. It is also the fallback when a skill was not among the assessed
proficiencies.

search_project runs the same RAG pipeline, but over this project-overview
document instead of the candidate's data, in a separate vector collection. It
answers questions about the system itself and about how the agent works —
architecture, technology stack, the RAG pipeline, the skill scorer, the
evaluation suite, deployment, and design decisions — including second-person
questions addressed to the agent ("how do you work?", "what model are you?",
"what reranker do you use?"). This is the tool serving the very answer you are
reading.

The router prompt distinguishes the two RAG tools by subject: a question about
the candidate goes to search_documents; a question about the software project or
how the system/agent works goes to search_project. The separate synthesis prompt
governs the answer itself — ground every claim in the retrieved context, never
invent facts, say plainly when the context does not answer the question, never
state or invent a numeric skill rating, stay concise and professional, and
always answer in the same language the recruiter used. Personal and out-of-scope
questions are declined by saying only professional career information can be
shared, without mentioning tools, fields, or how the system works internally.


THE PROVIDER-NEUTRAL LLM CLIENT

Every LLM interaction in the project — tool scoring, answer synthesis, the
broad/specific query router, query expansion, and the build-time document
summaries — goes through a single provider-neutral client.

The client has three backends. OpenRouter is the production default: a unified
API that reaches any model from any provider through one endpoint, which is what
makes the model choice a pure configuration value rather than a code path. The
Anthropic backend talks to the Claude API directly. The Ollama backend talks to
a local model server — the original local stack, and still what the evaluation
judges run on, so a full evaluation costs nothing. For local reasoning models
the client strips any <think> reasoning block from the output so only the final
answer is surfaced. Switching providers is a configuration change; no calling
code changes.

Three model roles are configured independently rather than one model serving
everything. AGENT_MODEL writes the final answer, ROUTER_MODEL classifies
broad versus specific, and TOOL_SELECT_MODEL does the tool scoring. Splitting
them means the cheap, highly structured job — emitting four numbers and their
arguments as JSON — can sit on a small fast model while answer synthesis, where
quality is actually visible to the recruiter, stays on a stronger one. The role
is passed explicitly on every call rather than inferred from the model id, which
was ambiguous whenever two roles happened to be configured to the same model;
the role is also what the telemetry log attributes each call's cost to.


THE RAG PIPELINE — INGESTION

Documents are parsed with the Unstructured library, backed by PyMuPDF for PDFs,
python-docx for Word files, and OCR via Tesseract and Pillow for images. The
parser performs section-aware extraction rather than dumping flat text. It
detects section headers — including unusual spaced-letter headers like
"T E C H N I C A L  S K I L L S" via a dedicated regular expression — and
merges consecutive elements under the same heading into one section block.

Deciding what is a heading and what is content is subtler than it looks, and
getting it wrong is expensive because every chunk is stored with its section
name prepended, so a bad name becomes embedded noise on the front of everything
beneath it. Three rules do the work. A leading section number is stripped before
anything else, so "6.3 The probabilistic router" is recognised as a heading
while "GPA: 94.3" is not — an earlier version rejected any heading containing a
digit, which swallowed every numbered heading and collapsed a 127 KB document
with 99 headings into a single section. Elements carrying emails or telephone
markers are content, not headings. And anything too long, or a complete sentence
of more than a few words, is prose the partitioner mislabelled as a title.

Encoding is pinned rather than detected. Unstructured sniffs the encoding with
chardet and cannot be told otherwise — passing an explicit encoding is accepted
and then silently dropped, because the Markdown partitioner re-reads the file
through its own detector. That detector decided one valid UTF-8 document was
windows-1251 and corrupted every non-ASCII character in it. Text files are now
decoded up front and the decoded string is handed to the partitioner, so there
is no guess left to get wrong; binary formats still go through the normal path.

Each section is then split with a recursive character text splitter (about 1000
characters per chunk with 150 characters of overlap, preferring to break on
paragraph, line, sentence, then word boundaries). Every chunk is prefixed with
its section name for retrieval context ("Section: <name>") and stored with
provenance metadata: the source file and a document id. This provenance is
essential — it lets any retrieved chunk be traced back to its origin document,
which is what makes retrieval evaluation against ground-truth evidence possible.

Alongside the per-chunk index, a separate summary index is built. For each
document the LLM writes a short factual summary, which is embedded and stored in
its own ChromaDB collection. This summary index powers the "broad" retrieval
path described below.

The summary rubric follows the document's type, and this matters more than it
sounds. A rubric demanding a name, a degree and years of experience is
unanswerable for a project write-up; applied to one it produced stored refusals
("unable to provide the requested summary"), and worse, summaries that adopted
whatever name appeared in the text as the candidate's own identity. Since the
summary index is the answer path for the single most likely opening question —
"tell me about this candidate" — a stored refusal is read out to a recruiter
verbatim. There are now four rubrics. A CV is summarised by who the candidate
is; a project write-up by what the work does, with an explicit instruction not
to infer identity or employment from it; a recommendation letter by who wrote it
and what they attest to; a certificate by what it certifies and what it records.
Every rubric ends with the same contract: summarise what the document actually
contains, never refuse, never ask for a different document, and simply omit any
point the document does not cover.

There is also a lighter in-memory ingestion path for text that is already plain
(no file parsing, no summary) — used, for example, when the skill-scorer
training corpus is ingested verbatim so the model sees exact text.

One property of the index is worth stating because it is a trap: chunk and
summary ids are deterministic (the source filename plus section and chunk
indices), and ChromaDB silently ignores a write to an id that already exists.
Re-uploading a document therefore never duplicates it, but also never replaces
it — a bad summary survives its own re-ingestion. Correcting one requires
deleting first, which is what the reindex utility does before it re-ingests.


THE RAG PIPELINE — RETRIEVAL

Retrieval is a multi-stage pipeline designed for both recall and precision.

First, query routing. An LLM router classifies each incoming query as BROAD (a
general "who is this person / give me an overview" question) or SPECIFIC (any
particular fact, skill, project, or detail). Broad queries are answered from the
compact summary index, which gives a clean high-level picture; specific queries
go through the full fusion path below.

Second, query expansion. For specific queries the LLM generates several query
variations — a deliberate mix of short keyword-style queries, which favor sparse
search, and natural-language queries, which favor dense vector search — to
maximize recall across both retrieval methods.

Third, hybrid fusion retrieval. For every query variation the system runs both
dense vector search (semantic similarity over embeddings in ChromaDB) and sparse
keyword search (BM25 Okapi) over the chunk corpus. All the resulting ranked
lists are merged with Reciprocal Rank Fusion (RRF). RRF scores each list
independently by reciprocal rank, so a top result in any single list is rewarded
regardless of that list's length or origin; this fuses keyword and semantic
signals without having to calibrate their raw scores against each other.

Fourth, re-ranking. A cross-encoder reranker rescores the fused candidate pool
against the original query and keeps the best top-k chunks, which become the
context handed to the agent.

A deliberate design touch: the pipeline exposes the fused candidate pool from
before re-ranking. This lets the evaluation suite localize exactly where a
relevant chunk was lost — at ingestion (it was never indexed), at recall (it
never entered the fused pool), or at re-ranking (it entered the pool but was cut
from the final top-k) — turning a single aggregate recall number into an
actionable, per-stage diagnosis.

The embeddings are asymmetric: documents and queries are embedded with different
prefixes ("search_document:" versus "search_query:"), which matches how the
embedding models were trained and improves retrieval quality. Because the stored
document vectors bake in the document prefix, switching the embedding provider
requires rebuilding the vector index.


SKILL PROFICIENCY ESTIMATION — THE FLAGSHIP FEATURE

Rather than leaving "how good is the candidate at X?" to keyword matching, the
project trains a dedicated NLP model to score each skill from 1 to 5 directly
from the candidate's own documents. The scale is ordinal and defined as: 1 =
awareness (a passing mention), 2 = working familiarity, 3 = competent /
day-to-day use, 4 = strong / leads work in it, 5 = expert / authority.

At setup time, for each skill the candidate lists, the system retrieves that
skill's supporting evidence chunks from the candidate's documents (routing and
summary are off here, because a bare skill name is always a specific query) and
runs the trained scorer. The 1-to-5 result is shown to the candidate right there
in the setup page as private feedback — a visual, ranked view that tells them
which skills are well-supported and which need more evidence — so they can
strengthen a weak profile before sharing it. Only the evidence chunks are written
into the structured store; the numeric score is deliberately never persisted and
never exposed to recruiters. The recruiter chat then answers skill questions from
that curated evidence instantly via get_skill_proficiency — grounded in real
passages but without quoting a score — instead of recomputing or guessing at
query time.

The scorer itself is a fine-tuned DeBERTa-v3 transformer with a CORAL ordinal
regression head. CORAL is used because the 1-to-5 levels are ordered, not
arbitrary categories — confusing a 4 with a 5 is a smaller error than confusing
a 1 with a 5, and an ordinal head encodes that structure. The model reads the
skill name plus its evidence chunks, serialized in exactly the format it saw in
training ("{skill} {sep} {chunk1} {chunk2} ..."). The best-performing
configuration fine-tunes the top transformer layers; head-only and plain-softmax
classifier variants were also trained and compared, and the ordinal CORAL
configuration won. Because the scorer (and document parsing) only run at build
time, neither is ever deployed to the always-on service.


GPU MEMORY MANAGEMENT DURING SCORING

When the local stack is used, the DeBERTa scorer and the local Ollama LLM
contend for the same GPU. The DeBERTa model with disentangled attention is
memory-heavy, and a resident Ollama model with multiple parallel slots can
occupy most of the card. To run both on a modest GPU, the build phase
time-slices the device: just before the scoring burst it asks the Ollama server
to evict its model from VRAM, runs the scorer, and then unloads the scorer and
clears the CUDA cache so Ollama can reload (honoring its parallelism) for the
question-answering work. The batch size of the scorer is also tunable via an
environment variable. None of this applies to the API stack, where no local
model is resident.


SYNTHETIC TRAINING DATA GENERATION

Training the skill scorer required labeled (skill, evidence, level) data that
does not exist publicly, so the project includes a full synthetic data
generation system. It builds realistic candidate personas and archetypes,
generates documents containing controlled skill evidence at known proficiency
levels, tracks phrase usage across generations to avoid repetition, sanitizes
the output, and validates the corpus with statistical checks, cross-validation,
and shortcut-detection analysis — the latter to ensure the model learns from
genuine evidence rather than spurious surface cues (such as a level always
co-occurring with a particular phrase). Generation uses asynchronous LLM calls
for throughput. The result is a labeled dataset large and clean enough to
fine-tune an ordinal scorer that generalizes to real documents.


PLUGGABLE PROVIDERS

Three layers are pluggable purely through configuration, with no code changes,
and this is what lets the same codebase run fully local or fully cloud.

The LLM layer is OpenRouter (production default, reaching any provider's model
through one API), the Anthropic API directly, or a local Ollama model. All LLM
uses — tool scoring, synthesis, router, query expansion, build summaries — go
through the one provider-neutral client described above, and each of the three
model roles can name a different model.

The embeddings layer is either the Voyage AI API (production default, no local
model) or a local nomic-embed-text model via sentence-transformers. Both are
asymmetric document/query embedders.

The reranker layer is either the Voyage rerank API (production default), a local
Qwen3-Reranker, or "none" to skip reranking. The Qwen3 reranker is notable: it
is a causal language model, not a classification cross-encoder, and is scored —
per its model card — by reading the probability of the "yes" token at the final
position of a query/document relevance prompt, rather than with a naive
classification head.

The local backends are constructed lazily, so importing the embedder or reranker
modules in the production (API) configuration never imports PyTorch or
transformers. This is the mechanism that keeps the serve image torch-free while
preserving the original "built entirely from local open-source models" story.


OBSERVABILITY — PER-TURN TELEMETRY

Every recruiter turn is recorded: the question asked, the per-tool routing
scores, which tools ran, whether escalation fired, the answer given, wall-clock
latency, and for each underlying LLM call its model, role, token counts and
cost. A conversation id ties a session's turns together, so the record is
readable as a conversation rather than a pile of isolated calls.

Cost is taken from the provider's own reported usage where it is available —
OpenRouter returns an authoritative figure per call — and falls back to a local
price table only when it is not. A hard-coded price table alone goes stale the
moment a provider changes pricing, and silently reports confident wrong numbers.

Records are written to two sinks at once: standard output and a JSON-lines file.
Both exist because a hosted container's filesystem does not survive a redeploy
while its log stream does, so the file is the convenient local view and stdout
is the durable hosted one. Because the selected tools run concurrently in a
thread pool, the active turn is carried on a context variable that is copied
into each worker, rather than threaded through every call signature by hand.

The Usage and Conversations dashboard reads this log. It answers the practical
questions an owner actually has: what has this cost so far, which questions are
slow, which tools the router leans on, and what recruiters are really asking.


CONFIGURATION SYSTEM

All of the above is driven by a central settings module. Each setting resolves
in priority order: an environment variable first, then a Streamlit secret, then
a default. This means the same code reads local environment variables on a
developer machine or a GPU pod and reads managed secrets when deployed to a
Streamlit host, without branching. The defaults target the production all-API
configuration. (The settings module is named "settings" rather than "config" on
purpose, to avoid colliding with the skill estimator's own internal flat
"config" module, which is imported by the scoring code under its own directory.)

Beyond the provider choices, the notable settings are the application mode
(production serves only the recruiter chat; setup mode also exposes the
candidate page), the shared access code and the separate admin password, the
three model roles, the tool-selection threshold and the escalation switch, and
the telemetry toggle and log path.


STRUCTURED STORE AND VECTOR STORE

The structured store is a small JSON file holding the verified profile fields
plus, per listed skill, the supporting evidence found in the documents — but not
the model's numeric score, which is candidate-private and never written to disk.
It is the source for get_structured_data and get_skill_proficiency, both of which
therefore answer instantly and deterministically.

The vector store is ChromaDB, used as a persistent on-disk index with cosine
similarity. Each candidate's chunks live in their own collection, with a paired
"_summaries" collection for that candidate's summary index. This project overview
lives in its own separate collection ("project_kb", plus its summary
collection), which is what the search_project tool queries — keeping project
knowledge cleanly isolated from candidate data so the two can never bleed into
each other's retrieval.


THE EVALUATION SUITE

The project ships a rigorous, component-based evaluation harness rather than
ad-hoc spot checks. It runs the full agent over golden datasets and scores
several independent dimensions.

Tool Selection: did the agent pick the correct tool — structured facts versus
skill scorer versus candidate document search versus project search — for each
question?

RAG Quality: RAGAS metrics (faithfulness, context precision, context recall, and
answer relevancy) computed on the RAG-routed questions, using the retrieved
contexts captured during the run.

Answer Correctness: DeepEval's GEval LLM-as-judge on every question, scoring
whether the final answer is correct and appropriate, including whether refusals
are worded correctly.

Refusal Accuracy: a confusion matrix checking that the agent refuses
out-of-scope or inappropriate questions and does not refuse legitimate ones.

Router Accuracy: did the broad/specific router classify each query correctly
against its labeled route?

Per-gate Retrieval Analysis: for specific document questions with known evidence,
it localizes exactly where a relevant chunk was lost — at ingestion, at recall,
or at re-ranking — using the pre-rerank fused pool the pipeline exposes.

Ingestion Quality: chunk statistics, coverage, and summary quality.

The harness seeds each candidate's data into a fresh collection, runs the
pipeline over that candidate's questions, then scores every component on the
combined result set and generates an HTML report (with companion JSON and CSV)
showing both per-candidate and aggregate breakdowns. It supports checkpointing
and resuming, so a long run can be interrupted and continued.

Generation and judging are deliberately split. Answers are produced by the
hosted API stack — exactly what a recruiter receives — while the judges run on
local Ollama models. That means evaluating the system costs nothing, and no
answer is graded by the model family that wrote it.

The most recent full run covers 490 questions across six candidates plus the
project knowledge base, on the production stack. Answer correctness scores
90.3%, faithfulness 93.3%, tool-selection accuracy 91.4%, refusal accuracy 94.1%
with zero hallucinations, and retrieval reaches the answer 96.3% of the time.
Context precision is 84.9%, answer relevancy 83.0%, context recall 82.4%.

The weak spots are kept visible rather than buried. The broad/specific router is
the weakest component at 82.9%, and its errors are lopsided — 44 false-specific
against 6 false-broad. Refusal accuracy also reads healthier than it is: the
confusion matrix shows 10 of the 30 should-refuse questions were answered
anyway. Nothing was hallucinated, but the agent engages with out-of-scope
questions more than intended. Retrieval gate localization is what turned an
aggregate recall number into a decision: it identified the re-ranker as the
primary bottleneck, which drove a targeted upgrade rather than a guess.


THE EVALUATION DATA

Evaluation uses six synthetic candidates with deliberately varied document
formats — PDF, DOCX, TXT, Markdown, and image/PNG specifically to exercise the
OCR path. Each candidate has a golden dataset of around 75 questions spanning
personal facts, education, experience, preferences, skills, skill proficiency,
projects, certifications, complex multi-tool questions, and deliberately
out-of-scope "negative" questions that the agent should refuse. A separate
project-knowledge dataset asks questions about this system itself; those
project questions are routed to search_project and evaluated the same way as the
candidate document questions, so adding the new tool did not require a new
scoring path. The pre-existing candidate evaluation data was left unchanged when
the project dataset and tool were added.


DEPLOYMENT AND SECURITY

The recruiter chat deploys to a Streamlit-based host such as Streamlit Community
Cloud or Hugging Face Spaces, served over HTTPS. Access is gated by a single
shared access code, which suits a single-candidate app: there is exactly one
person to protect and one link to hand out, so a single secret is the right
strength. With no access code configured the gate is a no-op, which is
convenient for local development. Once a recruiter authenticates, the result is
cached in session state so they are not re-prompted on every interaction.

Several security properties are enforced by design. In production only the
recruiter chat is registered, so recruiters can neither edit the profile nor
trigger ingestion; the page directory is deliberately not named "pages" so
Streamlit cannot publish those routes behind the gate's back; and each page
verifies authentication itself as a second layer. The usage dashboard sits
behind a separate admin password compared in constant time.

The candidate's private data is kept out of any public repository by
construction. The source repository is public — it is the portfolio artifact —
but the vector database and the structured profile are ignored by version
control and can never be committed to it by accident. The running app still
needs them, so publishing is done by a script that force-adds exactly those two
artifacts onto a commit built in a throwaway worktree and pushes it to a
separate private repository, which is the one the host builds from. The script
refuses to run if the two remotes resolve to the same place, verifies the index
is actually non-empty before pushing (a present-but-empty index is the failure
that looks like success — the app deploys fine and then answers every question
with "I don't have that information"), and strips the evaluation suite and the
trained scorer weights, tens of megabytes the serve path never executes.

API keys live only in environment variables or managed secrets and are never
committed. This very project-overview document is intentionally free of private
information and secrets.

Running costs are minimal and, unusually, measured rather than estimated: the
telemetry log records the real cost of every turn, so the running bill is a
number the owner can read rather than a guess. The all-API serve path uses a
fast, inexpensive model for synthesis and an even cheaper one for tool scoring,
plus a low-cost Voyage tier for embeddings and reranking — typically only a few
dollars per month of light use — and the hosting itself can be free. The
expensive work (training the scorer, generating synthetic data, parsing
documents, running the full evaluation) all happens locally at build time and
adds nothing to the hosting bill.


TECHNOLOGY STACK

Frontend and app framework: Streamlit, multi-page, with a shared design-token
module and a custom theme. LLM and orchestration: OpenRouter (or the Anthropic
API directly, or local Ollama), probabilistic multi-tool routing with concurrent
execution and result-based escalation, a provider-neutral client with three
independently configurable model roles. Embeddings: Voyage AI (or local
nomic-embed via sentence-transformers). Retrieval: ChromaDB for dense vectors,
BM25 Okapi for sparse search, Reciprocal Rank Fusion, and a cross-encoder
reranker (Voyage rerank or Qwen3-Reranker). Skill scoring: DeBERTa-v3 with a
CORAL ordinal head, in PyTorch and Hugging Face Transformers. Ingestion:
Unstructured, PyMuPDF, python-docx, Tesseract OCR, type-specific LLM summary
rubrics, and section-aware recursive chunking via LangChain text splitters.
Observability: per-turn cost, latency and conversation logging to JSON lines and
stdout, with a password-gated dashboard. Evaluation: RAGAS and DeepEval (GEval),
plus custom tool, router, refusal, and per-gate retrieval evaluators, with HTML,
JSON, and CSV reports. Configuration: a central settings module resolving
environment variables, then Streamlit secrets, then defaults.


DESIGN PRINCIPLES AND WHAT MAKES IT NOTABLE

The standout engineering choices are: a trained, evidence-grounded skill scorer
instead of keyword guessing; probabilistic multi-tool routing that scores every
source independently and runs the ones that clear a bar concurrently, with a
result-based escalation net, rather than forcing a single-tool choice; a hybrid,
fused, re-ranked retrieval pipeline fronted by a broad/specific router and query
expansion; a serious multi-dimensional evaluation suite, including the per-gate
retrieval failure localization that pinpoints whether recall or re-ranking lost
a chunk; a fully synthetic, validated training-data pipeline built because the
needed labels did not exist; per-turn cost and latency telemetry that makes the
running system's behaviour and bill observable rather than assumed; and a clean
build-versus-serve split with three pluggable provider layers that lets one
codebase run entirely on free local open-source models or deploy as a cheap,
secured, always-on cloud service.

The guiding principles throughout are grounding (never answer beyond the
evidence), verifiability (every skill claim and fact traces back to a source),
honesty (refuse the unknown and the out-of-scope, and publish the evaluation's
weak numbers alongside the strong ones), and portability (local for building and
proving, cloud for serving).
